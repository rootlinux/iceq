# IceQ Threat Model

Last reviewed: 2026-07-16. This is a repository threat model, not an independent cryptographic audit or a production penetration test.

## Scope, assets, and trust boundaries

Assets are account credentials and sessions, browser-held identity/session/sender keys, message and attachment plaintext, stored ciphertext, contact/group membership, delivery and presence metadata, recovery backups, infrastructure credentials, and (when explicitly enabled later) the Tor v3 private key.

The browser is the E2EE endpoint and therefore a trusted execution boundary. HTTPS/WSS terminates at Caddy; application services, NATS, Redis, PostgreSQL, ScyllaDB, and MinIO are inside the operator boundary. External trust boundaries include peers and their devices, browser/OS extensions, npm/Go/container dependencies, the clearnet and later Tor network, GitHub Actions, and backup storage. The server is not trusted with plaintext, but it remains trusted for availability, routing, membership authorization, public-key distribution, and metadata handling.

## Threats, current mitigations, and residual risk

| Threat | Current repository mitigation and evidence | Residual risk / excluded guarantee |
|---|---|---|
| Server compromise | DM Signal operations live in `web/src/lib/signal.ts`; group Sender Keys live in `web/src/lib/groupCrypto.ts` and `web/src/lib/senderKeys.ts`; attachments use client-side AES-GCM in `web/src/lib/fileCrypto.ts`. Tests: `web/tests/signal-wire-format.test.ts`, `signed-prekey-verification.test.ts`, `sender-keys.test.ts`, `file-crypto.test.ts`. | A compromised server can deny/delay traffic, alter public bundles or membership responses, retain ciphertext/metadata, and serve malicious JavaScript. Safety verification helps detect identity substitution but does not make a compromised web origin safe. No independent crypto audit has occurred. |
| Malicious or compromised peer | Identity-change send/decrypt blocking is implemented in `web/src/lib/identityTrust.ts`, `indexeddb.ts`, and `signal.ts`; QR/text comparison is in `web/src/components/Settings/SafetyQr.tsx`. Strict group payload validation is in `groupCrypto.ts`. | A legitimate recipient can copy plaintext, attachments, and keys. E2EE cannot prevent screenshots, exports, harassment, or endpoint compromise. |
| Traffic analysis and metadata disclosure | Caddy deletes common client-IP, User-Agent, Authorization, and Cookie log fields and skips WS/message transport logs in `deploy/Caddyfile`; presence/receipt controls are in `web/src/hooks/usePresence.ts` and privacy tests. | The service necessarily observes timing, sizes, account identifiers, contact/group membership, routing and online activity. No padding, mix network, cover traffic, or complete metadata anonymity is claimed. |
| Browser compromise | CSP and browser headers are defined in `deploy/Caddyfile`; keys are client-side/IndexedDB; decrypted chat state is memory-only. Tests include `service-worker-policy.test.mjs`, `direct-protobuf-dependency.test.mjs`, and `curveasm-build.test.mjs`. | XSS, a malicious extension, compromised dependency, OS compromise, or malicious code served by the origin can access plaintext and keys while the app runs. At-rest browser key encryption is not a guarantee. |
| Dependency/supply-chain compromise | Lockfiles, `npm ci`, `npm audit`, `govulncheck`, `go vet`, tests, and SHA-pinned CI actions are enforced by `.github/workflows/security-ci.yml`. | Audits are signature/advisory based and cannot prove dependencies or build infrastructure are benign. Container images are not yet digest-pinned. |
| Replay/duplicate delivery | DM ratchet handling and deterministic durable ingest/receipt/outbox paths are in `backend/message-service/store/durable_ingest*.go`; gateway idempotency is in `backend/ws-gateway/router/idempotency.go`. Tests: `durable_ingest_test.go`, `router/idempotency_test.go`, `recipient_acceptance_test.go`. | Availability failures and delayed delivery remain possible; recipient devices may retain previously accepted plaintext. |
| Membership churn and stale group keys | Server-visible `crypto_epoch`, membership-bound snapshots, sender-key inbox, and client pruning are implemented in migrations `008`-`013`, `backend/message-service/handlers/groups.go`, and `web/src/lib/groupCrypto.ts`. Tests: `group-crypto-store.test.ts`, `group_epoch_ingest_test.go`, `group_sender_key_test.go`. | Epoch rotation limits future access; it cannot erase messages or sender keys already received by a removed member. The server still sees membership. |
| File abuse | Ownership/grants are in migrations `006`/`007` and `backend/file-service/handlers/files.go`; canonical object keys, MIME/name checks, encrypted manifests, and size limits are in `web/src/lib/fileCrypto.ts`. Tests: `file-crypto-limits.test.ts`, `attachment-grant-lifecycle.test.ts`, file-service authorization tests. | MinIO availability/storage exhaustion, malware inside encrypted files, and a recipient redistributing decrypted content are not prevented. Operators still need quotas, monitoring, and abuse response. |
| DoS/resource exhaustion | Edge and authenticated rate limits, request-size checks, Compose resource limits, bounded polling/outbox work, and timeouts are present in `deploy/Caddyfile`, `backend/shared/middleware`, service handlers, and `deploy/docker-compose.yml`. | A sufficiently large distributed attack or infrastructure failure can make IceQ unavailable. No availability SLA or DDoS absorption guarantee exists. |
| Session theft and destructive abuse | HttpOnly/Secure/SameSite refresh cookies, rotation/reuse response, CSRF signal, session epochs, durable wiped-account marker, and panic wipe are in auth/JWT middleware. Tests: `refresh_test.go`, `csrf_test.go`, `wiped_account_test.go`, `panicwipe_handler_test.go`. | Stolen active access tokens remain usable until expiry/revocation checks; panic wipe is irreversible and cannot erase recipient devices or backups already made. |

## Explicitly excluded guarantees

IceQ does not guarantee endpoint security, peer honesty, availability, complete anonymity, deletion from recipient devices/backups, protection from a malicious web build, safety without out-of-band fingerprint comparison, or cryptographic correctness certified by an independent auditor. Tor assets are opt-in scaffolding only: runtime boot, consensus publication, onion reachability, and DNS-leak testing are deferred until after clearnet real-user acceptance.
